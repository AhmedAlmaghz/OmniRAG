# تقرير مراجعة احترافي — OmniRAG SDLC

**تاريخ المراجعة:** 13 أغسطس 2026  
**نطاق المراجعة:** الحزمة الموجودة في `SDLC` (36 ملفاً، معظمها وثائق Markdown)  
**نوع المشروع المراجع:** مواصفات هندسية ومنتج وخطة تشغيل لمنصة RAG هجينة ثنائية اللغة، وليست مستودعاً تنفيذياً قابلاً للتشغيل حالياً.

---

## 1. الملخص التنفيذي

تقدّم الحزمة تصوراً طموحاً ومنظماً لمنصة **OmniRAG**: استرجاع هجين عربي/إنجليزي، عزل متعدد المستأجرين، معالجة مستندات متعددة الوسائط، طبقة MCP للوكلاء والتكاملات، حوكمة أمنية، واختبارات وتقييمات للذكاء الاصطناعي.

**التقييم العام للوثائق: 7.8 / 10.**

نقطة القوة الأساسية هي عمق التصور: المتطلبات، المخاطر، الحماية، التقييمات، التشغيل، وخارطة الطريق موثقة بصورة أفضل من أغلب مشاريع RAG في مرحلة التصميم. لكن الفجوة بين التصميم والتنفيذ كبيرة: لا توجد شيفرة تطبيق، ولا `package.json`، ولا إعداد CI فعلي، ولا مخططات migrations أو OpenAPI أو fixtures أو Golden Sets حقيقية. لذلك لا يمكن اعتبار المشروع جاهزاً للإطلاق أو حتى لـ MVP برمجي؛ بل هو **Blueprint قوي يحتاج إلى تقليص نطاق، تثبيت قرارات، وتحويل العقود إلى artefacts تنفيذية قابلة للاختبار**.

**الأولوية القصوى:** بناء MVP صغير وآمن أولاً (رفع ملفات + Private RAG + عزل tenant + citations)، وتأجيل معظم التكاملات وMCP والإجراءات الخارجية إلى مراحل لاحقة.

## 3. نقاط القوة

### 3.1 تحليل منتج ناضج

- تعريف واضح للرؤية: RAG هجين مع أولوية للخصوصية والعربية والإنجليزية.
- تقسيم جيد لأوضاع الاستخدام: Private RAG، Hybrid Web+RAG، General Chat، Analysis، وAgentic.
- حالات الاستخدام والمصادر المدعومة واسعة وتغطي الملفات، الويب، التكاملات، وقواعد البيانات.
- توثيق صريح للحالات الحدية: ملفات فارغة، PDFs ممسوحة/محمية، ترميز عربي، استعلامات بلا نتائج، انقطاع البث، وتعارضات المحتوى.

### 3.2 أمن وعزل متعدد المستأجرين قوي على مستوى التصميم

- الدفاع متعدد الطبقات موثق بصورة جيدة: JWT، RLS، فلترة Qdrant، مسارات Blob المعزولة، وAPI middleware.
- تضمين حالات اختراق cross-tenant كاختبارات مطلوبة يعد قراراً صحيحاً جداً.
- وجود متطلبات للإجراءات الحساسة: تأكيد بشري، تدقيق، rate limiting، idempotency، timeouts وallowlists.
- اهتمام مناسب بأسرار OAuth، التشفير، وسلسلة الإمداد البرمجية.

### 3.3 نضج ملحوظ في الجودة وعمليات الذكاء الاصطناعي

- توجد مقاييس جودة RAG مناسبة: Recall@K، MRR، NDCG، faithfulness، ودقة المراجع.
- توثيق Golden Sets، LM-as-a-Judge، بوابات CI، وكشف الانحدار يقدم أساساً جيداً لـ LLMOps.
- دعم العربية لا يقتصر على الترجمة؛ بل يشمل RTL، التطبيع، التشكيل، النص المختلط، ومعايير تقييم عربية.

### 3.4 تشغيل وصيانة مدروسان

- تعريف SLOs، Error Budgets، المراقبة، trace IDs، وسجل المخاطر جيد.
- خارطة الطريق تقسم الإطلاق إلى آفاق مفهومة وتحتوي معايير دخول مرحلية.
- تعليمات الوكلاء واضحة في مبدأ عدم تجاوز العزل أو التعامل مع أسرار وبيانات إنتاج.

### 3.5 جودة هيكل التوثيق

- الملفات منظمة بحسب مراحل SDLC.
- وجود `INDEX.md` لكل حزمة يسهّل التصفح.
- الروابط المحلية سليمة، وهي نتيجة جيدة وقابلة للحفاظ عليها عبر فحص آلي في CI.

## 4. الفجوات والمخاطر الرئيسية

### P0 — يجب معالجتها قبل بدء التنفيذ الموسع

#### 4.1 لا يوجد منتج تنفيذي حتى الآن

المجلد لا يحتوي على تطبيق Next.js أو خدمات أو migrations أو tests أو CI. وجود مقتطفات TypeScript وSQL في Markdown لا يعني وجودها كأصول قابلة للبناء.

**الأثر:** لا يمكن قياس الالتزام بالأمن، الأداء، أو الجودة فعلياً.

**التوصية:** إنشاء مستودع تنفيذ أولي فوراً يتضمن:

- Next.js + TypeScript strict.
- مدير حزم واحد فقط (`pnpm` موصى به).
- `package.json`, lint, typecheck, test, build.
- CI أساسي في GitHub Actions.
- Docker Compose محلي لـ Postgres/Qdrant أو بدائل testcontainers.
- `.env.example` بدون أسرار.

#### 4.2 تضخم نطاق MVP (Scope Creep)

المواصفة تجمع في الإصدار الأول: 15+ مصدر بيانات، OCR متعدد المحركات، فيديو وصوت، محرك Agentic، MCP Gateway، OAuth لخوادم خارجية، analytics، API SDK، web search، ومزايا enterprise/امتثال متعددة.

**الأثر:** تأخر شديد، تكاليف غير متوقعة، واتساع سطح الهجوم.

**التوصية:** تقليص MVP إلى:

1. مصادقة + tenant واحد لكل حساب.
2. رفع PDF/DOCX/TXT/Markdown فقط.
3. استيعاب غير متزامن مع محرك واحد مبدئي.
4. Qdrant + Postgres metadata.
5. Private RAG فقط مع citations إلزامية.
6. العربية/الإنجليزية وواجهة RTL.
7. قياسات أساسية وrate limits.

ويؤجل: MCP، web search، البريد/Slack/Notion، الصوت/الفيديو، Agentic mode، API public، multi-region، HIPAA وteam workspaces.

#### 4.3 قرارات تقنية غير مثبتة أو عرضة للتغير

تذكر الوثائق نسخاً ومواصفات مستقبلية/غير متحقق منها للنماذج وMCP مثل `gemini-3.6-flash` وMCP `2026-07-28` وحزم SDK v2.0. يجب ألا يصبح التصميم معتمداً على أسماء أو واجهات SDK قبل التحقق من وثائق المزود في وقت التنفيذ.

**التوصية:**

- بناء طبقة `ModelProvider` و`EmbeddingProvider` و`McpTransport` خلف interfaces مستقرة.
- نقل model IDs وdimensions وtoken limits وpricing إلى configuration versioned.
- كتابة اختبارات contract مع المزود الفعلي قبل اعتماد أي API.
- تعريف fallback واضح؛ لا تفترض أن نماذج من مزود آخر متوافقة فقط لأن أبعاد المتجهات متشابهة.

#### 4.4 تناقضات في أهداف الاحتفاظ والامتثال

هناك اختلافات بين الوثائق في مدد حفظ سجلات MCP والتدقيق والنسخ الاحتياطية (مثلاً 180 يوماً مقابل 7 سنوات، واحتفاظ audit logs بمدد مختلفة). كما وردت إشارات إلى "HIPA" بدلاً من HIPAA في وثيقة التشغيل.

**الأثر:** خطر امتثال، تضارب في التنفيذ، وعدم وضوح سياسة حذف البيانات.

**التوصية:** إعداد وثيقة واحدة مصدر حقيقة باسم `data-retention-policy.md` تشمل:

- نوع البيانات، التصنيف، المدة، المنطقة، أساس المعالجة، الحذف، النسخ الاحتياطية، ومسؤول الموافقة.
- توحيد تعريف Audit Log مقابل Access Log مقابل MCP Call Log.
- مراجعة قانونية فعلية قبل الادعاء بدعم GDPR/HIPAA/PCI أو BAA.

#### 4.5 نموذج tenant غير مناسب لتوسع B2B

المواصفة تجعل `tenant_id` فريداً في جدول `users` وبعلاقة 1:1، وفي الوقت نفسه تذكر مستقبلاً workspaces وفرقاً. هذا سيجعل الانتقال إلى multi-user workspaces مكلفاً لاحقاً.

**التوصية:** حتى لو بقي MVP فردياً، صمم الآن الجداول بهذه العلاقات:

- `tenants` مستقل.
- `users` مستقل.
- `tenant_memberships(tenant_id, user_id, role)`.
- جميع الموارد تشير إلى `tenant_id`.

هذا يحافظ على بساطة MVP ويمنع migration صعباً لاحقاً.

### P1 — مهمة قبل Beta/Production

#### 4.6 RLS المقترح يحتاج صلابة أعلى

استخدام `current_setting('app.current_tenant')::UUID` يمكن أن يفشل أو يسبب سلوكاً غير آمن إذا لم تُضبط قيمة الجلسة دائماً أو إذا استُخدم دور يتجاوز RLS.

**تحسينات مطلوبة:**

- تفعيل RLS أيضاً على `users` وجميع جداول tenant-scoped؛ لا تكتفِ بالقائمة الحالية.
- استخدام `current_setting('app.current_tenant', true)` مع دالة آمنة تتعامل مع null.
- ضبط السياق داخل transaction بـ `SET LOCAL` وليس إعداد جلسة متسرباً عبر connection pooling.
- منع صلاحيات `BYPASSRLS` وملكية الجداول عن دور التطبيق.
- فرض `FORCE ROW LEVEL SECURITY` عندما يلزم.
- اختبار تكامل حقيقي بدور قاعدة بيانات التطبيق، وليس mock أو superuser.

#### 4.7 Qdrant وPostgres يحتاجان نمط اتساق واضح

التصميم يستخدم تخزيناً مزدوجاً (Postgres/Qdrant) لكن لا يحدد التنفيذ الفعلي للتزامن، رغم الإشارة إلى transactional outbox في ADR.

**التوصية:** تطبيق Outbox Pattern:

1. كتابة document/chunks/event في معاملة Postgres واحدة.
2. Worker يقرأ outbox ويفهرس Qdrant بشكل idempotent.
3. حالة event وإعادة المحاولة وDLQ.
4. reconciliation job يومي للتحقق من `chunks.embedding_id` ووجود النقطة وtenant المطابق.

#### 4.8 واجهات API ليست عقداً قابلاً للتشغيل

قائمة endpoints جيدة، لكنها لا تحدد schemas، response envelopes، pagination، error codes، idempotency headers، أو versioning/deprecation بصورة كاملة.

**التوصية:** اعتماد OpenAPI 3.1 مصدر حقيقة، ثم توليد:

- Zod validators في السيرفر.
- client SDK/typed clients.
- contract tests وSchemathesis/fuzzing.
- توثيق أخطاء موحد يعتمد `application/problem+json` أو envelope موحد.

#### 4.9 سياسة citations والثقة تحتاج تعريفاً رياضياً وتشغيلياً

المطلوب "كل ادعاء" مدعوم بمصدر، لكن لا توجد آلية claim extraction أو grounding verifier محددة. كما أن confidence score غير معرف بدقة وقد يضلل المستخدم.

**التوصية:**

- فصل "Retrieval confidence" عن "Answer groundedness" وعدم عرض رقم موحد غير مفسر.
- البدء بسلوك قابل للضبط: no-answer عند عدم بلوغ threshold + عرض مصادر الاسترجاع.
- تطبيق citation validator حتمي: chunk موجود، tenant مطابق، snippet يدعم النص، والرابط صالح.
- قياس claim support offline قبل تفعيل وسم ثقة في UI.

#### 4.10 استراتيجية البحث العربي المعجمي تحتاج تجربة فعلية

`tsvector` القياسي لا يقدم بالضرورة stemming/normalization عربياً بالمستوى المطلوب. التطبيع قبل الفهرسة قد يضر النص الأصلي، خصوصاً النصوص المشكولة والدينية.

**التوصية:**

- الاحتفاظ بحقلين: `content_original` و`content_normalized`.
- قياس PostgreSQL FTS العربي مقابل محرك BM25 يدعم Arabic analyzers أو حلول هجينة بديلة.
- عدم إزالة التشكيل افتراضياً؛ اجعلها سياسة قابلة للضبط كما تقترح الوثائق.
- إنشاء golden set عربي حقيقي قبل تثبيت الأوزان أو خوارزمية الدمج.

### P2 — تحسينات نوعية وتحرير توثيقي

#### 4.11 MCP هو أعلى سطح خطر ويجب تأجيله

توثيق MCP غني جداً، لكنه يحوّل التطبيق إلى منصة تنفيذ خارجية (Slack, email, webhooks, GitHub). هذا يضاعف الأعباء الأمنية والتشغيلية.

**التوصية:**

- لا تضف T3 side-effect tools في MVP أو Beta المبكرة.
- ابدأ بأدوات قراءة داخلية فقط (search/retrieve).
- لا تثق بـ `tenant_id` الذي يصل كمعامل أداة؛ استخرجه من هوية الخادم فقط. يمكن تمريره داخلياً، لكنه لا يجب أن يكون مصدر التفويض.
- طبق SSRF protection حقيقية: URL parsing، DNS re-resolution protection، منع IP ranges الداخلية، redirects policy، outbound proxy.
- استخدم capability tokens ضيقة النطاق، وسجل تدقيق append-only خارج قاعدة التشغيل عندما يصبح ذلك ضرورياً.

#### 4.12 بعض ادعاءات الأداء والتكلفة تحتاج أدلة

توجد نسب مثل توفير 60–70% أو تخفيض latency بنسبة 15%، وسعات/زمن معالجة محددة دون مصدر تجريبي داخل المشروع.

**التوصية:** إعادة صياغتها كـ **فرضيات** إلى أن تؤكدها benchmarks؛ ووضع ملف `benchmarks/baseline.md` يحتوي البيئة، corpus، الحمل، النتائج، وتاريخ القياس.

#### 4.13 تعارضات بسيطة في التوثيق

- مرجع `04-tasks.md` في متطلبات PRD لا يقابله ملف فعلي؛ الموجود هو `04-spec-plan` بأسماء مختلفة.
- بعض ملفات التوثيق تشير إلى مسارات مستقبلية مثل `/docs/architecture.md` و`/runbooks/` و`/evals/` لكنها غير موجودة في الحزمة.
- README ضخم جداً ويكرر كثيراً من التفاصيل؛ سيتعرض للانحراف عن الوثائق المتخصصة.

**التوصية:**

- اجعل README مدخلاً مختصراً (vision، quickstart، architecture summary، links).
- انقل التفاصيل إلى الوثائق المتخصصة، وحدد "Source of Truth" لكل موضوع.
- أضف فحص CI للروابط وللمسارات المرجعية داخل Markdown.

## 6. خطة تطوير عملية مقترحة

### المرحلة 0 — تثبيت الأساس (أسبوع 1)

- اعتماد مالك منتج وDRI أمن وDRI هندسة.
- حسم الأسئلة المفتوحة P0: مزود auth، مزود LLM، region، محرك jobs، نموذج البيانات، وسياسة retention.
- إنشاء repository تنفيذي، conventions، CI، CODEOWNERS، `.env.example`، وقرار package manager.
- تحويل العلاقات والمتطلبات الحرجة إلى backlog قابل للتتبع.

**مخرج المرحلة:** مشروع يبني ويجتاز lint/typecheck/test فارغاً لكن حقيقياً.

### المرحلة 1 — Secure Private RAG MVP (أسابيع 2–5)

- Auth + `tenants/users/memberships` + RLS مختبر.
- رفع PDF/DOCX/TXT/MD بمحددات حجم/MIME/hash.
- Outbox + worker للاستيعاب + Qdrant/Postgres reconciliation.
- بحث semantic أولاً، ثم lexical بعد benchmark عربي/إنجليزي.
- Private chat فقط: citations، no-answer، streaming، rate limit، audit metadata.
- 20–30 اختباراً أساسياً تشمل cross-tenant وملفاً عربياً ونصاً مختلطاً.

**معيار القبول:** مستخدمان تجريبيان لا يستطيع أي منهما رؤية بيانات الآخر؛ ملف عربي قابل للاستعلام مع مرجع صحيح.

### المرحلة 2 — الجودة والتشغيل (أسابيع 6–8)

- Golden set أولي: 50 عربي + 50 إنجليزي للاسترجاع، و20+20 للتوليد.
- CI: unit/integration/E2E/security smoke/link checker.
- OpenTelemetry، metrics، dashboards أساسية، error catalog، cost tracking.
- SLOs أولية واقعية مبنية على قياس staging وليس افتراضات.

**معيار القبول:** قياس baseline منشور، وعدم وجود تسرب tenant، ونجاح eval gates المتفق عليها.

### المرحلة 3 — Hybrid Search ومصادر منتقاة (أسابيع 9–12)

- إضافة RRF بعد إثبات فائدة semantic وlexical على golden set.
- مصدر URL واحد أو GitHub واحد، مع SSRF/robots/rate-limit controls.
- settings الضرورية فقط، وحذف/تصدير بيانات وظيفي ومختبر.

### المرحلة 4 — MCP قراءة فقط ثم الإجراءات (بعد إثبات الاستقرار)

- MCP read-only مع خوادم curated قليلة وتكامل OAuth مدروس.
- side effects لاحقاً فقط، مع confirmation state machine، idempotency، sandbox، ومراجعة أمنية خارجية.

## 8. الخلاصة النهائية

OmniRAG يملك **تصميماً وثائقياً طموحاً ومتميزاً**، وبالأخص في العزل، دعم العربية، تقييمات RAG، وحوكمة MCP. القوة الحالية هي في مستوى التفكير والتخطيط، لا في الجاهزية التنفيذية. النجاح سيتوقف على مقاومة إغراء بناء كل شيء دفعة واحدة: ابدأوا بـ Private RAG موثوق ومثبت الاختبارات، ثم أضيفوا التعقيد عبر مراحل مدعومة بالقياس.

**القرار المقترح:** اعتماد الحزمة كمرجع تصميم مبدئي مشروط، والبدء فوراً بمرحلة "Foundation + Secure Private RAG MVP" بعد توحيد القرارات الحرجة وسياسات البيانات.
