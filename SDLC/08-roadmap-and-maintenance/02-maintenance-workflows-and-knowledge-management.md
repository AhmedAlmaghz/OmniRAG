# Maintenance Workflows and Knowledge Management

> القسم الثاني من حزمة خارطة طريق التطوير وصيانة OmniRAG. يُغطّي هذا القسم سير عمل الصيانة الدورية، ونموذج تشغيل الفريق، واستراتيجية توثيق قابلة للتوسع مع نمو قاعدة الشيفرة والميزات. يُفترض أن تكون قد اطّلعت على [Evolution Roadmap and Technical Debt Policy](./01-evolution-roadmap-and-technical-debt-policy.md) لتفهم الأفق الزمني الذي تُنفّذ ضمنه هذه الصيانة.

---

## 1. مبادئ التشغيل الأساسية (Operating Principles)

| المبدأ | الوصف | مقياس التحقق |
|---|---|---|
| **التوثيق كعقد (Documentation as Contract)** | كل تغيير في الكود يصحبه تحديث في الوثائق في نفس PR | فحص CI يربط PR بالملفات في `/docs` |
| **الاختبارات والتقييمات كعقد (Tests & Evals as Contract)** | ما لا يختبره وكيل فهو غير موجود | تغطية اختبارات ≥ 80% + 100% من المسارات الحرجة مُقيّمة |
| **التغييرات الصغيرة والمتكررة (Small, Frequent Changes)** | كل PR ≤ 400 سطر؛ نشر متعدد المرات يومياً | تقرير Trunk-Based Development |
| **التشغيل القابل للملاحظة (Observable Operations)** | كل خدمة ولها سجلات (Logs) + قياسات (Metrics) + آثار (Traces) | لوحة SLO مُفعّلة لكل بيئة |
| **الأمان بالتصميم (Security by Default)** | مراجعة أمنية لكل ميزة تتعامل مع بيانات حساسة (GDPR/HIPAA/PCI) | قائمة مراجعة مكتملة قبل الدمج |

## 2. نظام الإيقاعات (Cadence System)

تعتمد OmniRAG نظام إيقاعات متعدد الطبقات مستوحى من Scrum@Scale و Continuous Delivery، مُكيَّف مع طبيعة الوكلاء الذكيين الذين يؤدون جزءاً كبيراً من التنفيذ.

### 2.1 الإيقاع اليومي

| النشاط | الوقت | المسؤول | المُخرج |
|---|---|---|---|
| مراجعة PRs المفتوحة | 09:00 UTC | مهندس مناوب (Rotating Reviewer) | إغلاق ≥ 90% من PRs المُفتوحة من اليوم السابق |
| مراقبة لوحة SLO | كل ساعة (آلياً) | On-call Engineer | تنبيه عند انحراف > 2σ |
| فحص سجلات الأخطاء | 12:00 و 18:00 UTC | On-call Engineer | تصنيف الحوادث (P0/P1/P2/P3) |
| تحديث لوحة Kanban | لحظي | كل عضو | تحديث حالة المهام |

### 2.2 الإيقاع الأسبوعي

| النشاط | اليوم | المدة | الحضور | المُخرج |
|---|---|---|---|---|
| **Sprint Planning** | الإثنين | 60 دقيقة | الفريق كامل + وكيل تخطيط (Conductor) | Sprint Backlog مُعتمد |
| **Daily Standup** | الإثنين–الجمعة | 15 دقيقة | الفريق كامل | تحديد العوائق |
| **Architecture Review** | الأربعاء | 45 دقيقة | مهندس معماري + قائد تقني | ADR (Architecture Decision Record) للمقترحات |
| **Security Review** | الخميس | 30 دقيقة | Security Champion | تقييم الثغرات المُكتشفة |
| **Sprint Retrospective** | الجمعة | 45 دقيقة | الفريق كامل | 3 تحسينات مُلزمة للأسبوع التالي |
| **Maintenance Window** | الأحد 02:00–04:00 UTC | ساعتان | DevOps Engineer + بوت صيانة | نشر تحديثات، تنظيف، نسخ احتياطية |

### 2.3 الإيقاع الشهري

| النشاط | الهدف | المُخرج |
|---|---|---|
| مراجعة Technical Debt Register | رصد الدين المتراكم وتحديث أولوياته | تقرير أولويات الشهر القادم |
| ترقية التبعيات (Dependencies) | تحديث الحزم، معالجة الثغرات المُعلنة | PR تبعيات + سجل التغييرات (Changelog) |
| مراجعة تكاليف البنية التحتية | تحسين استخدام الموارد على Vercel/Neon/Qdrant | توصيات بحوالي 10-15% تخفيض |
| مراجعة Evals | تقييم دقة RAG وجودة الوكيل | تحديث Benchmark Results |
| تقييم أداء الفريق | مراجعة المخرجات مقابل OKRs | تقرير OKR مُحدّث |

### 2.4 الإيقاع الربع سنوي

| النشاط | الهدف |
|---|---|
| تخطيط الأفق (Horizon Planning) | مراجعة خارطة الطريق في [Evolution Roadmap](./01-evolution-roadmap-and-technical-debt-policy.md) |
| مراجعة التدقيق الخارجي (External Audit) | فحص أمني واختراق (Penetration Test) |
| تحديث وثائق المستخدم | مواءمة `/docs` مع واجهة المستخدم الفعلية |
| Disaster Recovery Drill | اختبار استعادة النسخ الاحتياطية |

## 3. نموذج تشغيل الفريق (Team Operating Model)

### 3.1 الأدوار والمسؤوليات

| الدور | المسؤوليات | عدد الأفراد | التناوب |
|---|---|---|---|
| **Tech Lead** | القرارات المعمارية، مراجعة ADRs، تنسيق الوكلاء | 1 | — |
| **Conductor Engineer** | تفكيك المتطلبات لمهام بحجم وكيل، صياغة AGENTS.md prompts | 2 | ربع سنوي |
| **Backend Engineer** | Next.js API، RAG Engine، MCP Gateway | 2 | — |
| **Frontend Engineer** | واجهة `/dashboard`، `/chat`، `/mcp-hub` | 2 | — |
| **AI/ML Engineer** | هندسة الأوامر (Prompt Engineering)، تقييمات النموذج، توجيه النماذج | 1 | — |
| **Data Engineer** | خط أنابيب الاستيعاب، Qdrant، Neon Schema | 1 | — |
| **Security Engineer** | RLS، OAuth، اختبار الاختراق، الامتثال | 0.5 (مشترك) | — |

| **Doc Steward** | حارس جودة الوثائق، مراجعة PRs التوثيقية | 0.5 (تناوب) | شهري |

### 3.2 مصفوفة RACI للأنشطة الرئيسية

| النشاط | Tech Lead | Conductor | Engineer | SRE | Security | Doc Steward |
|---|---|---|---|---|---|---|
| اعتماد PR معماري | **A** | C | R | I | C | I |
| صياغة مهمة وكيل | C | **A/R** | C | I | I | I |
| نشر إنتاج | A | I | I | **R** | C | I |
| استجابة حادث P0 | A | I | C | **R** | C | I |
| تقييم أمني | C | I | C | I | **A/R** | I |
| مراجعة وثائق | I | C | C | I | I | **A/R** |
| تحديث Technical Debt | **A** | R | R | C | C | I |

> **A** = Accountable, **R** = Responsible, **C** = Consulted, **I** = Informed

## 4. سير عمل الصيانة الدورية (Recurring Maintenance Workflows)

### 4.1 ترقية التبعيات (Dependency Upgrade)

**التكرار:** شهري (يوم الثلاثاء الأول) | **المسؤول:** Migration Agent تحت إشراف Backend Engineer

```
┌─────────────────────────────────────────────────────────────┐
│           سير عمل ترقية التبعيات                             │
│                                                             │
│  1. الفحص (Monday)                                          │
│     └─ Migration Agent يفحص @latest عبر npm                 │
│     └─ يصنف: Major / Minor / Patch / Security              │
│                                                             │
│  2. الفرز (Tuesday morning)                                  │
│     └─ ترتيب حسب: أمنية > كسر API > إصلاحات               │
│     └─ استثناء ما يتعارض مع Qdrant/Neon SDK                │
│                                                             │
│  3. التنفيذ (Tuesday afternoon)                              │
│     └─ فتح PR منفصل لكل ترقية كبرى                        │
│     └─ تشغيل CI الكامل (Unit + Integration + Eval)         │
│                                                             │
│  4. التحقق (Wednesday)                                       │
│     └─ نشر على بيئة Staging                                 │
│     └─ تشغيل 50 استعلام Eval للتأكد من عدم الانحدار       │
│                                                             │
│  5. الدمج والإصدار (Thursday)                                │
│     └─ مراجعة بشرية إذا كانت ترقية Major                   │
│     └─ نشر إنتاجي مع Canary Release (10% → 100%)           │
└─────────────────────────────────────────────────────────────┘
```

**معايير النجاح:**
- لا ترقية `major` تُنشر يوم الجمعة
- كل ترقية `security` تُنشر خلال 48 ساعة من الإعلان
- تقرير PR يوثّق نتائج `pnpm audit` قبل وبعد

### 4.2 النسخ الاحتياطي واستعادة البيانات (Backup & Recovery)

| البيئة | نوع النسخة | التكرار | الاستبقاء | الموقع |
|---|---|---|---|---|
| **Neon Postgres** | Snapshot تلقائي | كل ساعة | 7 أيام | Neon Cloud |
| **Neon Postgres** | Snapshot يومي | 02:00 UTC | 30 يوماً | Neon Cloud |
| **Neon Postgres** | تصدير منطقي (pg_dump) | أسبوعياً | 1 سنة | Vercel Blob (مشفّر) |
| **Qdrant Collections** | Snapshot كامل | يومياً | 14 يوماً | Qdrant Cloud S3 |
| **Vercel Blob (Files)** | مكررة تلقائياً | مستمر | حسب `dataRetention` | Multi-Region |
| **OAuth Tokens** | مُشفّرة بـ AES-256 | فوري | مع دورة حياة الرمز | Neon `mcp_oauth_tokens` |

**معيار الاستعادة (RTO/RPO):**

| الحادث | الهدف | التحقق |
|---|---|---|
| فقدان قاعدة بيانات | RTO ≤ 30 دقيقة، RPO ≤ 1 ساعة | Drill ربع سنوي |
| فقدان مجموعة Qdrant | RTO ≤ 2 ساعة، RPO ≤ 24 ساعة | Drill نصف سنوي |
| فقدان OAuth Tokens | إعادة ربط تلقائي | اختبار آلي أسبوعي |

### 4.3 صيانة قاعدة البيانات

| المهمة | التكرار | السكربت | المُنفّذ |
|---|---|---|---|
| `VACUUM ANALYZE` | أسبوعياً (الأحد 03:00 UTC) | `pg_cron` job | آلي |
| إعادة بناء الفهارس (REINDEX) | شهرياً | migration script | Migration Agent + Backend |

| تدوير مفاتيح AES-256 | ربع سنوي | سكريبت يدوي | Security Engineer |

| أرشفة محادثات > 90 يوم | يومياً | `pg_cron` | آلي |

## 5. إدارة الحوادث (Incident Management)

### 5.1 مستويات الخطورة

| المستوى | الوصف | زمن الاستجابة | زمن الحل المستهدف | التصعيد |
|---|---|---|---|---|
| **P0** | انقطاع كامل للخدمة أو خرق بيانات | ≤ 15 دقيقة | ≤ 4 ساعات | CEO + Tech Lead فوري |
| **P1** | ميزة رئيسية معطلة (RAG/Chat/Auth) | ≤ 30 دقيقة | ≤ 24 ساعة | Tech Lead خلال ساعة |
| **P2** | تدهور في الأداء أو خطأ في ميزة ثانوية | ≤ 4 ساعات | ≤ 5 أيام | — |
| **P3** | خطأ تجميلي أو تحسين | ≤ 48 ساعة | Sprint التالي | — |

### 5.2 سير عمل الحادث (Incident Workflow)

```
[الكشف] → [الترياج] → [الاحتواء] → [التحقيق] → [الحل] → [مراجعة ما بعد الحادث]

  Triage Agent    On-call       Tech Lead       Incident Commander
  (آلي)          Engineer     (إذا P0/P1)      (مدير الحادث)
```

### 5.3 قالب مراجعة ما بعد الحادث (Post-Mortem Template)

كل حادث P0 أو P1 يُنتج مستند Markdown يحوي:

```markdown
# Post-Mortem: [عنوان الحادث]

## الملخص
- **التاريخ:** YYYY-MM-DD
- **المدة:** HH:MM
- **المستوى:** P0 | P1
- **المكتشف:** [نظام المراقبة | مستخدم | مهندس]
- **Incident Commander:** [الاسم]

## الجدول الزمني (بتوقيت UTC)
- 14:32 — تنبيه من Datadog (p95 latency > 5s)
- 14:35 — On-call يصنّف الحادث P1
- 14:42 — Tech Lead يُبلّغ
- 15:10 — السبب الجذري مُحدّد: Qdrant collection overflow
- 15:35 — الحل المؤقت: زيادة shard count
- 16:02 — الخدمة تعود لطبيعتها

## السبب الجذري (Root Cause)
[شرح تقني مفصّل]

## التأثير
- عدد المستخدمين المتأثرين: ~XXX
- الاستعلامات الفاشلة: ~XXX
- الإيرادات المفقودة: $XXX (إن وُجد)

## الإجراءات التصحيحية
| الإجراء | المسؤول | الموعد | الحالة |
|---|---|---|---|
| [إجراء 1] | [اسم] | YYYY-MM-DD | ✅/🔄/⏳ |
| [إجراء 2] | [اسم] | YYYY-MM-DD | ✅/🔄/⏳ |

## الدروس المستفادة
1. [درس 1]
2. [درس 2]

## كيف نمنع تكراره
[إجراءات وقائية]
```

### 5.4 التعلم من الحوادث

- كل Post-Mortem يُضاف إلى `docs/postmortems/` ويُفهرس
- Agent Skills خاصة بالحوادث المتكررة تُنشأ من الدروس (مثال: `mcp-token-rotation-playbook`)
- Post-Mortem يُعرض في Retro الفريق التالي

### 6.2 معايير التوثيق الإلزامية

لكل تغيير يُدمج في `main` يجب أن يُستوفى أحد الشرطين التاليين:

| نوع التغيير | متطلبات التوثيق |
|---|---|
| ميزة جديدة | قسم في `00-PRODUCT-OVERVIEW.md` + تحديث API Reference |
| تغيير API | تحديث `02-API-REFERENCE` + Changelog |
| تغيير معماري | ADR جديد في `01-ARCHITECTURE/adr/` |
| ميزة وكلاء جديدة | تحديث `04-AGENT-GUIDES` |
| Runbook جديد/مُعدّل | تحديث `03-RUNBOOKS` |
| اكتشاف ثغرة | إضافة إلى `05-COMPLIANCE` |

### 6.3 فهرسة وقابلية الاكتشاف

| التقنية | الهدف | الأداة |
|---|---|---|
| **بحث دلالي في الوثائق** | إيجاد محتوى الوثائق بسرعة | Qdrant (instance مخصص للوثائق) |
| **توليد Embeddings للوثائق** | تحديث فهرس البحث أسبوعياً | `gemini-embedding-2` |
| **روابط داخلية** | ربط الوثائق ببعضها | GitHub-flavored Markdown |
| **رسم بياني للقرارات (ADR Graph)** | تصور القرارات المعمارية | Mermaid diagrams |
| **مخطط التبعية (Doc Dependency Map)** | تتبع الوثائق المتأثرة بتغيير | `docs-lint` أداة داخلية |

### 6.4 دورة حياة الوثيقة (Document Lifecycle)

```
  [المسودة] → [المراجعة] → [الاعتماد] → [النشر] → [الأرشفة]

     Draft      Review       Approved     Live     Archived
     (DRAFT)    (IN-REVIEW)  (CURRENT)    (LIVE)   (DEPRECATED)
```

**حالات الوثيقة (Document Status):**

| الحالة | الوصف | الإجراء عند التغيير |
|---|---|---|
| `DRAFT` | قيد الكتابة | يُسمح بالتعديل المباشر |
| `IN-REVIEW` | بانتظار مراجعة | يحتاج موافقة 2 مراجعين |
| `CURRENT` | معتمدة وفعّالة | يحتاج PR + مراجعة |
| `DEPRECATED` | لم تعد صالحة | تبقى متاحة + لافتة "مهمل" |

**سياسة الإهمال (Deprecation Policy):**
- أي وثيقة `CURRENT` تُستبدل تصبح `DEPRECATED` لمدة 6 أشهر قبل الأرشفة
- لافتة واضحة في أعلى الوثيقة تُشير للاستبدال
- روابط إعادة توجيه (Redirects) في CI

### 6.5 توثيق القرارات المعمارية (ADRs)

كل قرار معماري مهم يُوثّق في ملف ADR بالتنسيق:

```markdown
# ADR-XXXX: [عنوان القرار]

## الحالة
PROPOSED | ACCEPTED | DEPRECATED | SUPERSEDED

## السياق
ما المشكلة التي نعالجها؟

## الخيارات المُقارنة
| الخيار | المزايا | العيوب |
|---|---|---|
| الخيار A | ... | ... |
| الخيار B | ... | ... |

## القرار
ما الذي قررناه؟

## العواقب
- إيجابيات
- سلبيات
- مخاطر

## التاريخ
YYYY-MM-DD — [الاسم] قبل/اعتمد
```

## 10. حوكمة الوكلاء (Agent Governance)

### 10.1 حدود صلاحيات الوكلاء

| الوكيل | الصلاحيات | القيود |
|---|---|---|
| **Conductor Agent** | قراءة ملفات، كتابة ملفات في `/sprints/` | لا يصل للإنتاج |
| **Coder Agent** | تعديل كود، تشغيل اختبارات | لا يُدمج PRs، لا يصل لـ DB الإنتاج |
| **Reviewer Agent** | قراءة كود، نشر تعليقات | لا يُعدّل ملفات |
| **Migration Agent** | تشغيل migrations في staging | لا يُشغّل migrations الإنتاج بدون موافقة بشرية |
| **Test Writer Agent** | كتابة اختبارات | لا يُعدّل كود الإنتاج |
| **Doc Writer Agent** | كتابة/تحديث ملفات `/docs` | لا يُعدّل الكود |
| **Eval Judge Agent** | تشغيل evals + كتابة تقارير | لا يُعدّل الإعدادات |

### 10.2 سجل قرارات الوكلاء (Agent Decision Log)

كل قرار مهم يتخذه وكيل يُسجّل في:

```json
{
  "timestamp": "2026-08-15T14:32:11Z",
  "agent": "Conductor Agent",
  "decision_type": "task_decomposition",
  "input_context": {
    "prd_section": "3.4 Chat Interface",
    "estimated_complexity": "high"
  },
  "output": {
    "tasks_created": 8,
    "delegated_to": ["Frontend Engineer", "AI/ML Engineer"]
  },
  "model_used": "gemini-3.6-flash",
  "tokens_consumed": 4521,
  "human_review_required": false
}
```

### 10.3 التقييم المستمر للوكلاء

| المقياس | الوصف | الحد الأدنى |
|---|---|---|
| **Task Success Rate** | نسبة المهام التي يكملها الوكيل بدون تدخل بشري | ≥ 70% |
| **Code Acceptance Rate** | نسبة PRs المُولّدة التي تُقبل بعد المراجعة | ≥ 60% |
| **Eval Score Stability** | ثبات درجات التقييم عبر الزمن | انحراف معياري < 0.05 |
| **Hallucination Rate** | نسبة المخرجات غير الصحيحة في تقييمات الوكيل | < 3% |
| **Token Efficiency** | متوسط الرموز لكل مهمة ناجحة | مقياس نسبي |

### 10.4 ترقية وتدريب الوكلاء

| الإجراء | التكرار | المالك |
|---|---|---|
| مراجعة prompts الوكلاء | شهرياً | Conductor Engineer |
| اختبار نماذج جديدة في دور الوكلاء | ربع سنوي | AI/ML Engineer |
| توسيع Agent Skills | عند كل درس مستفاد | Conductor Engineer |
| أرشفة إصدارات الوكلاء | عند كل release | DevOps |
